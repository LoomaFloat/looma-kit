# Переделка кода в движок

Общий приём один: найти функцию «вход → результат на карте», загрузку модели вынести в
`load()`, само вычисление в `compute()` каркаса ([Каркасы](templates.md)), вход и выход
перевести в HTTP. Ниже частые случаи. Перед каждым проверь, не хватает ли модели каталога
(`looma models`) или своих весов на движке площадки (`looma model check --repo …`): тогда
движок не нужен.

## Пайплайн diffusers (изображения, видео)

- `load()`: `DiffusionPipeline.from_pretrained(os.environ.get("LOOMA_MODEL") or "…",
  torch_dtype=torch.float16).to("cuda")`; LoRA и планировщик там же.
- `compute()`: промпт и параметры из JSON, изображение в PNG байтами
  (`Content-Type: image/png`) или JSON с base64 для нескольких.
- `kinds: [api]`, `weights: hf` (если модель задаёт автор модели) или `none`.
- Единица счёта: изображение (`X-Looma-Units: 4` за четыре) или секунда видео.
- Видео и всё дольше минуты: долгое задание (`/long` в каркасе), ход в процентах по
  шагам денойзинга через `callback_on_step_end`.
- `requires`: `vram_gib` по размеру модели в fp16 плюс запас 2–4 ГиБ.

## Модель transformers (текст)

- Чат: начни с [engines/llm](https://github.com/LoomaFloat/looma-kit/tree/main/engines/llm),
  поменяй загрузку и шаблон. `kinds: [text]`.
- Не чат (классификация, извлечение, перевод с особым форматом): свой API, вход и выход
  JSON.
- Если модель открыта и архитектура обычная, сначала попробуй своя модель на движке
  площадки (`looma model add --repo …`): своего кода не нужно.

## Сервер модели (vLLM, TGI, llama.cpp) у проекта

- Модель открытая, safetensors: своя модель на движке площадки `vllm` или `torch`.
- GGUF, особые флаги, свой форк сервера: движок, который запускает сервер дочерним
  процессом на локальном порту и проксирует к нему `/v1/chat/completions`; `/health`
  отвечает 200, когда отвечает дочерний сервер. Пакеты сервера в `requirements.txt`.

## ComfyUI

Граф ComfyUI движком автора не делают: он становится своей моделью на движке площадки
`comfyui` без своего кода (skill `looma`, `references/models.md`, «Граф ComfyUI»; разбор
графа: `looma comfy inspect`). Наборы узлов (custom nodes) подключаются расширениями этого
движка: одобренные видны в `looma comfy sets`, свой набор подают на ревью папкой с
`looma-extension.yaml` (`extends: comfyui`, блок `comfyui` с узлами; образец и правила в
skill `looma`, `references/recognize.md`, «Набор узлов на ревью»). Сюда приходят, только
когда набор ревью не пройдёт (ставит код при старте, ходит в сеть, двоичные файлы) и
заменить его узлы нельзя.

**Два пути.** Граф целиком держит свой ComfyUI внутри движка автора одним из двух
способов (сравнение и выбор: тот же раздел skill `looma`):

- **обёртка-процесс на своём узле** (`looma engine try`, без ревью): работает только на
  узлах автора. Ревью для сети она не пройдёт: ядро ComfyUI и наборы узлов служба ставит
  при старте, а подпись ревью покрывает только пакет и список зависимостей; положить ядро
  в пакет не дают пределы (400 файлов, 8 МБ, файл до 1 МБ);
- **движок-образ** (`image` и Dockerfile, `looma engine submit`): ComfyUI, зависимости и
  наборы узлов собраны в образ, ревью кода нет, работает только на машинах площадки в
  песочнице; время карт идёт автору в расходы.

Ниже общий рецепт, затем отличия образа.

**Как устроить обёртку-процесс** (большая часть верна и для образа):

- **Граф** в API-формате («Export (API)» в ComfyUI; формат редактора с `nodes` и `links`
  не исполняется) лежит в пакете файлом JSON. Входы запроса служба подставляет в поля
  узлов по таблице в коде: `{"prompt": ("6", "text"), "seed": ("3", "seed")}`. Граф
  целиком в запросе не принимай, если модель будут звать другие: так вызывающий исполнит
  на узле любой код наборов узлов.
- **Ядро ComfyUI.** При первом старте служба качает архив закреплённого выпуска с GitHub
  по HTTPS (`https://github.com/Comfy-Org/ComfyUI/archive/refs/tags/<тег>.tar.gz`),
  сверяет sha256, записанный в коде, и распаковывает в `LOOMA_CACHE_DIR`. Следующий старт
  берёт его оттуда. `git clone` не годится: `git` на узле нет. Строкой `requirements.txt`
  ядро не ставится: актуальной версии на PyPI нет (пакет `comfyui` там старая сборка
  2024 года, не брать).
- **Зависимости.** Строки `requirements.txt` ComfyUI этой версии перенеси в
  `requirements.txt` движка: только пакеты, до 64 строк, без параметров pip; `torch`,
  `torchvision`, `torchaudio` без версии. Пакет интерфейса `comfyui-frontend-package`
  оставь: без него сервер может не стартовать. Наружу интерфейс всё равно не открыт.
- **Запуск ComfyUI** дочерним процессом: `python main.py --listen 127.0.0.1 --port <свой
  порт, не LOOMA_SERVE_PORT> --extra-model-paths-config <файл>`, каталоги
  `--input-directory`, `--output-directory`, `--temp-directory` в `LOOMA_CACHE_DIR`; при
  нехватке видеопамяти `--reserve-vram`. ComfyUI-Manager не ставь. Наружу смотрит только
  служба на `127.0.0.1:$LOOMA_SERVE_PORT`.
- **Наборы узлов (custom nodes).** Каждый, что нужен графу, закрепи коммитом. Маленький
  набор клади в пакет движка, большой качай при старте архивом, как ядро; в
  `custom_nodes` клади ссылки на их папки. Их зависимости идут в `requirements.txt`
  движка. `install.py` ComfyUI сам не запускает: что он ставит, перенеси в зависимости.
  `prestartup_script.py` ComfyUI исполняет при каждом старте: прочитай его, прежде чем
  брать набор. Расширения движка (`extensions: true`) обёртке не нужны: в сеть она не
  выходит, а набор в пакете проще.
- **Веса.** По узлам-загрузчикам графа (`CheckpointLoaderSimple`, `UNETLoader`,
  `CLIPLoader`, `DualCLIPLoader`, `VAELoader`, `LoraLoader`, `ControlNetLoader`,
  `UpscaleModelLoader` и загрузчики наборов) составь список файлов и найди каждый в
  открытом репозитории HuggingFace. Загрузчики, которые выбирают файлы по пресету, а не
  по имени (`IPAdapterUnifiedLoader` и подобные), читай в коде набора: какие файлы и в
  какие папки они ищут. Файлы `.pt` и `.pth` бывают с исполняемым кодом (pickle): бери
  их только из известных репозиториев, закрепив ревизию. Служба качает их при старте `hf_hub_download` в
  `HF_HOME` (с `HF_HUB_DISABLE_XET=1`, повтор при обрыве) и раскладывает ссылками
  `models/<папка>/<имя файла из графа>` в `LOOMA_CACHE_DIR`; туда указывает
  `extra_model_paths`. Веса с Civitai или закрытые: попроси автора выложить их в открытый
  репозиторий, если лицензия позволяет. Токенов движку площадка не передаёт, а файлы с
  машины автора (`ComfyUI/models`) ему не видны: программа узла работает в контейнере со
  своим томом.
- **Исполнение.** `POST /prompt` с графом и `client_id`, затем `GET /history/<prompt_id>`,
  пока не появятся выходы; файлы забирать `GET /view?filename=…&subfolder=…&type=output`.
  Изображение на входе: `POST /upload/image`, имя файла в поле узла `LoadImage`. Ход для
  долгого задания даёт websocket `/ws?clientId=…` (сообщения `progress`: шаг из шагов).
- **Ответ.** Одно изображение телом (`image/png`), несколько: JSON с base64. Видео и всё
  дольше минуты: долгое задание (`/long` в [Каркасах](templates.md)). `X-Looma-Units` по
  числу изображений или секунд видео.
- **`/health`:** 503, пока качаются веса и стартует ComfyUI; 200, когда ComfyUI ответил
  на `GET /system_stats`. Дочерний ComfyUI упал: служба выходит с ненулевым кодом.
- **Манифест:** `kinds: [api]`, `weights: none` (файлы весов задаёт граф), `requires`:
  `vram_gib` по весам графа плюс 2–4 ГиБ, `ram_gib` с запасом: ComfyUI выгружает веса с
  карты в память.
- **Первый старт долгий:** ядро, зависимости и гигабайты весов. Предупреди автора и
  смотри `looma model logs`, а не перезапускай. Реплику, которая не стала готовой за
  час, площадка снимает и поднимает заново; скачанное в `HF_HOME` и `LOOMA_CACHE_DIR`
  остаётся, поэтому закачка должна продолжаться с места, а не начинаться заново.

**Движок-образ с ComfyUI.** Всё выше верно, кроме того, откуда берётся код и как служба
слушает:

- **Dockerfile:** основа с PyTorch и CUDA (`pytorch/pytorch` нужной версии: torch уже в
  образе, сборка не качает его заново); ядро ComfyUI закреплённого выпуска архивом с
  GitHub (`ADD` по ссылке выпуска со сверкой sha256 или распаковка в `RUN`); `pip install
  -r requirements.txt` ComfyUI; наборы узлов, закреплённые коммитами, в
  `custom_nodes/` (их `install.py` не нужен: зависимости ставь в Dockerfile сам); своя
  служба и граф. Веса в образ не кладут: служба качает их при старте.
- **Манифест:** блок `image` (`dockerfile`, `port`, `command`), `kinds: [api]`,
  `weights: none`; `requires`: `device: [cuda]`, `vram_gib` по весам графа плюс 2–4 ГиБ,
  `ram_gib` обязателен и в песочнице это жёсткий предел (ComfyUI выгружает веса с карты в
  память: закладывай их размер), `cpus`, `cuda` по версии CUDA образа.
- **Служба** слушает `0.0.0.0:$PORT` (порт из манифеста), ComfyUI внутри по-прежнему на
  `127.0.0.1` своим портом. Наружу только через прокси площадки (порты 80 и 443, адрес
  уже в `HTTPS_PROXY`; `huggingface_hub` берёт его сам). Постоянный каталог `/cache`
  (он же `LOOMA_CACHE_DIR`, `HF_HOME` внутри): веса переживают перезапуск реплики.
- **Сборка:** папка движка до 5000 файлов и 64 МБ, сборка на машине площадки до двух
  часов; ход и конец лога: `looma engine show`. Сейчас образ остаётся на машине площадки,
  где собран, и реплики модели встают только на неё.
- **Песочница:** одна карта на реплику, под номером 0; расчёты CUDA и `nvidia-smi` есть,
  кодирования видео на карте нет (видео кодируй процессором). На ComfyUI этот путь ещё не
  проверялся: после сборки сделай пробные вызовы на всех ветках графа и смотри
  `looma model logs`; наборы узлов с особыми библиотеками для карты могут не работать.
- **Подача:** `looma engine submit <папка>` только по прямой просьбе автора, как любая
  подача. Код образа другим авторам не показывается. Модель на образе нельзя держать
  «только на своих узлах».
- **Проверить до подачи** можно только у себя: `docker build` и запуск с картой
  (`--gpus all`), если у автора есть NVIDIA. Иначе первая проверка: сборка на площадке и
  пробные вызовы.

## Обучение, дообучение, рендер, симуляция, расчёт

- Своё API с долгим заданием: `POST /train` (параметры, ссылки на данные или файлы
  задания), ход в `X-Looma-Progress`, итог: веса или результат телом до 256 МБ, иначе
  ссылкой на своё хранилище.
- Промежуточное состояние (чекпойнты) в `LOOMA_CACHE_DIR`: при перезапуске реплики
  площадка пошлёт тот же запрос с тем же `X-Looma-Job`, служба продолжит с места.
- Для себя на своём узле: модель на движке с `--own`, звать `looma call … --async`.
- Единица счёта: секунды или шаги (`X-Looma-Units`).

## Пакетная обработка файлов

- Вход файлами задания (`POST /v1/files`, затем `files` в `POST /v1/jobs`); служба
  получает ссылки в `X-Looma-Files` и скачивает сама.
- Выход: архив или JSON с результатами; большой результат ссылкой.

## Бинарник или не Python

- Бинарник под Linux x86_64 с CUDA: Python-служба запускает его `subprocess` и отдаёт
  вывод; бинарник скачивается при старте по открытой ссылке или ставится пакетом.
- Нужны системные библиотеки, другой язык целиком: движок-образ (`image` и Dockerfile).
  Он встаёт только на машины площадки, на свой узел нет.

## Чего не делать

- Не держать веб, базу и вычисление в одном движке: веб и данные живут в сервисе, движок
  только считает (skill `looma`, «Сервис и движок вместе»).
- Не класть веса, данные и секреты в пакет: пакет до 8 МБ, ревью читает его целиком.
- Не открывать наружу порты и не слушать `0.0.0.0` у движка-процесса: только
  `127.0.0.1:$LOOMA_SERVE_PORT`.
- Не ставить пакеты при каждом запросе: зависимости ставит узел по `requirements`.
