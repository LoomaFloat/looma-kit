# Перенос проекта на Looma

Looma — площадка для веб-сервисов с моделями ИИ: хостинг, Postgres, S3-бакет, домен
с TLS и модели сети Looma по API. Приложение описывается файлом `looma.yaml` и
выкатывается командой `looma deploy`: сначала на staging, на prod — отдельной
командой. Этот skill ведёт перенос существующего проекта по шагам.

Пути `scripts/` и `references/` — относительно папки этого skill.

## Правила

1. **Сначала оценка и план, потом правки.** Код проекта не трогать, пока пользователь
   не согласился с планом.
2. **Только по прямой просьбе пользователя:** `looma promote` (prod), `looma publish`
   (карточка в каталоге), `looma destroy`, удаление данных.
3. **Секреты не писать в файлы и не повторять в ответах.** Значения задаёт пользователь:
   `looma secrets set ИМЯ=значение` в своём терминале.
4. **Правки — минимальные и по делу.** Не переписывать то, что площадке не мешает. Где
   дёшево, оставить проект запускаемым и вне Looma (значения из переменных окружения
   с прежними значениями по умолчанию).
5. **Если проект — git-репозиторий**, предложить вести перенос в отдельной ветке, чтобы
   все правки были видны одним диффом.
6. **Приметы оценки — повод посмотреть, а не приговор.** Каждую находку проверить по
   указанным строкам, прежде чем делать выводы.

## Шаг 0. Готовность

```bash
looma --version          # CLI есть?
looma whoami             # вход выполнен?
```

Нет CLI — дать пользователю команду установки (нужен `uv` или `pipx`):

```bash
uv tool install "git+https://github.com/LoomaFloat/looma-kit"
```

Нет входа — пользователь выполняет `looma login` сам: откроется браузер, вход
подтверждается в консоли Looma. Не просить у пользователя пароль или ключ в чат.

## Шаг 1. Оценка

```bash
python3 scripts/assess.py <папка проекта> --json
```

То же самое — `looma assess <папка> --json` или MCP-инструмент `looma_assess`. Ключ не
нужен. В ответе: стек, вердикт (`fits`, `changes`, `blocked`), находки с уровнем
(`blocker`, `change`, `risk`, `note`), местами `файл:строка` и ссылкой на справку,
имена секретов и черновик `looma.yaml`.

Дальше:
- открыть места из находок и подтвердить или отбросить каждую;
- прочитать README проекта: команда запуска, переменные, внешние сервисы;
- для блокеров прочитать [platform.md](references/platform.md) и решить, снимается ли
  блокер переделкой (свою модель — заменить моделью каталога, Redis — Postgres) или
  площадка этого не умеет вовсе.

Сообщить пользователю коротко: подходит ли проект, что мешает, сколько правок, какие
модели каталога понадобятся. Если есть блокеры, которые не снять, — сказать это
прямо и остановиться.

## Шаг 2. План

Список правок по файлам: что меняется и зачем, какие разделы манифеста, какие
секреты задать, что с данными (перенос существующих данных — отдельный вопрос
пользователю). Модели — по `looma models`: имя, тип, отвечает или спит. Дождаться
согласия.

Файлы, которые не нужны в релизе (данные, тесты с большими файлами), — в
`.loomaignore`.

## Шаг 4. Проверка до релиза

```bash
looma validate <папка проекта>
```

Ошибки манифеста приходят все сразу, с местом; модели из `gpu:` сверяются с
каталогом. Исправлять, пока не будет «манифест годится». Предупреждения о спящих
моделях — нормально: первый вызов поднимет модель и подождёт.

По желанию пользователя — запуск у себя: `looma dev` в его терминале (база и бакет —
в Docker, модели — настоящие, до 200 вызовов в сутки). Процесс долгий, его
останавливают Ctrl+C.

## Шаг 5. Релиз на staging и проверка

```bash
looma deploy <папка проекта>
looma check --env staging              # запрос к вебу через API владельца
looma logs --env staging               # если ответ не 2xx или процесс падает
looma status
```

Сборка не удалась — причина в хвосте лога, который печатает `looma deploy`. Процесс
падает — `looma logs`. Цикл «правка → validate → deploy → check» повторять, пока
staging не ответит как надо. Проверить и ключевые пути API (`looma check --path …`),
а не только главную. Если в манифесте `access: clients`, гость по публичному адресу
получит страницу входа: проверку делает `looma check` (через API владельца), а
`looma check --public` — проверка шлюза и входа.

Секреты, без которых приложение не стартует, пользователь задаёт до проверки:
`looma secrets set ИМЯ=значение`, затем `looma restart web --env staging`.

## Шаг 6. Отчёт

Записать `LOOMA_PORT.md` в корень проекта по шаблону [report.md](references/report.md):
вердикт, что изменено и почему, что не перенесено, адреса, секреты (только имена),
как обновлять и как перейти на prod. Показать пользователю итог и ссылку на staging.

## Дальше — только по просьбе пользователя

```bash
looma promote            # релиз со staging — на prod
looma publish            # карточка из раздела listing — в каталог, через модерацию
looma listing            # статус модерации
```

Эксплуатация уже перенесённого приложения (логи, откат, секреты, статистика) —
skill `looma-apps`.
